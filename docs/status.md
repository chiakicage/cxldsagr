# cxldsagr 研究状态

更新：2026-10-02。按研究者最新修正，将 ECHO 的 MFU/cache 策略与 DeepSeek MFU 问题列为 baseline 有效性的首要缺口；保留用户规模与复访压力的修正。

研究从 **sparse KV fetching 与 sparse attention 计算的重叠设计**出发，正在探索
**sparse attention GR serving** 是否是合适的应用场景。当前范围是 **HBM 与 CPU DRAM**。
最主要的未决问题是：如何建立有依据的 GR 任务、模型、数据和服务负载，并在其中说明
KV 容量约束、offload 开销及相对 ECHO 的设计价值。已有单卡、跨请求保留用户历史的
串行测量，但 **ECHO 实现的 MFU 和 cache 策略、DeepSeek 当前实现的 MFU 存在问题，
涉及它们的 baseline 比较尚不正确**。数值一致和计量记录完整不能证明基线实现合理。
具体根因和影响量尚未定位，相关 MFU、性能归因与方案排名暂停用于研究结论。
旧短轨迹也没有建立有效的用户规模与缓存容量压力对照；16K 的少量复访重建差异只能描述
原轨迹。下一步先修正基线并复测，同时核对实际用户和复用距离，再评价容量与重叠收益。

可以直接修改下面的表述、状态和卡点；下次 Supervisor 会据此更新相关判断和下一步任务。
四环节可以同时推进，已有设计不要求场景先定稿。

## 2. SOTA baseline 与 Motivation

- [ ] 覆盖主要相关方案，讲清它们的取舍，并量化目标场景中的关键问题。

当前候选论证是：**全 HBM 的容量约束 → CPU DRAM offload 的取数等待 → dense prefetch
的冗余 → sparse fetch 的重叠困难**。这是待分析和验证的思路线索，各环节尚未整体成立。

| 条目 / 要回答的问题 | 当前理解 | 状态与具体缺口 |
|---|---|---|
| **2.1 主要 baseline 是否覆盖？** | DeepSeek 的 HBM/ECHO/串行 sparse/dense 预取和 NOSA 的 HBM/串行 sparse/dense 预取/overlap 均有对照代码；共用请求和配额只是比较的必要条件 | **基线有效性需修正。** ECHO 的 MFU/cache 策略与 DeepSeek MFU 存在问题，不能把已运行或通过数值审计写成 baseline 已建立；SOTA 覆盖也待补 |
| **2.2 全 HBM 的问题是什么？** | 原 16K NOSA 轨迹中 HBM 有 13 次复访 miss、offload 为 0，但 4K/64K 及 DeepSeek 的复访均命中；配置用户数没有形成预期容量压力 | **规模与容量论证需补测。** 主对照必须覆盖 HBM miss/offload hit 和两者均 miss 的复用距离区间；只增加首次访问人数或放大 N 标签不能补足证据 |
| **2.3 CPU DRAM offload 的问题是什么？** | NOSA 保留历史能避免部分复访重建，但命中后的 offload 执行通常比 HBM 慢；16K 全请求均值仍为 HBM 最低 | **取舍已有观测，归因待分解。** 冷历史构建、缓存管理和稀疏执行均计时，不能把所有差值归为串行取数等待 |
| **2.4 Dense prefetch 的问题是什么？** | 整层历史预取保留稀疏 attention；搬运量、预取机会和调度开销都可能影响延迟 | **归因待核对。** 旧 DeepSeek/ECHO 排名受基线问题影响，不能据此认定 dense prefetch 的相对优势；NOSA 原输入上的观测不自动外推到其他模型或容量负载 |
| **2.5 与 ECHO 如何比较？** | 研究者指出 ECHO 实现的 MFU 与 cache 策略有问题，DeepSeek 实现的 MFU 也不正确；此前“模型内可比”的判断过强 | **当前对比不成立，待修正复测。** 先核对计算实现、MFU 统计边界和 cache 行为，再在同输入、预算与输出范围下重跑；不能把当前实现问题当成 ECHO 方法本身的缺陷，更不能跨模型直接排名 |

## 3. Challenge 与 Design

- [ ] 能解释真实困难、设计与困难的对应关系，以及相对已有方法的技术区别。

| 条目 / 要回答的问题 | 当前理解 | 状态与具体缺口 |
|---|---|---|
| **3.1 Sparse fetch 为什么难以重叠？** | 候选挑战仍是减少搬运并隐藏等待；128-token candidate 的三个历史档内部采样均未达到 90% 重叠 | **需要行为归因。** 已观察到适用范围差异，但选集产生、依赖链和可用计算窗口各自的影响尚未区分，不能直接归因于某一项 |
| **3.2 当前设计如何应对？** | NOSA 融合唯一历史读取与 sparse attention；旧短轨迹中，相对串行 sparse 的全请求均值在 20/21 个配置下降，但复访均值未稳定改善 | **原输入上的实现观测。** 这不能替代有效复访压力下的系统比较；全请求包含冷历史构建，不能外推为复访收益。NOSA 内部仍无有限 token/page slots 与淘汰 |
| **3.3 技术区别和研究贡献是什么？** | 希望在减少搬运的同时获得重叠收益 | **待总结。** 与 ECHO 和其他方案的实质区别尚未建立；系统名称、最终技术划分和贡献表述均未确定 |

| **4.1 整体系统收益是什么？** | 原数值记录只支持对应输入的输出一致性；涉及 ECHO/DeepSeek 的 MFU、效率归因和性能排名暂停采用，旧短轨迹也不能替代容量实验 | **基线修正与主实验均待完成。** 修正后以新 run ID 验收并替换受影响结果；使用共同完整轨迹，报告实际人数、首访比例和复访 miss，不强制配额或重挑种子制造优势 |
