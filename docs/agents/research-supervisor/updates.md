## 2026-10-06：三层 dense DMA 已验收，C10 继续独立补测

- **新增证据：**真实三层 H64K+A128 四方法完成新一轮 check、bench、profile。
  Dense DMA extend 为 5.986 ms，低于 serial sparse 的 6.534 ms，仍高于 HBM
  的 3.761 ms；ECHO 为 8.434 ms。所选下一层完整 H2D 的 50.21% 与当前层计算
  重叠，原生记录确认实际执行 `cudaMemcpyAsync`，没有用旧 gather 数字替代。
- **研究理解：**连续布局和 copy-engine 传输已在这个局部 baseline 范围形成可核验
  对照。该结果不证明 C10 serving 收益、ECHO 方法获益或 GR 场景质量；旧版本中
  dense 慢于 serial sparse 的排序不再代表当前三层实现。
- **影响与任务：**更新 2.4、2.5、4.1–4.2；T-007 移出已完成的三层补测，保留
  C10 DMA、关联容量更新及剩余归因。NOSA indexer workspace 仍未实施。
  原 A128 gather 报告在新结果验收后替换，依据见 S-032。

- **影响与任务：**2.4、2.5、4.1–4.2 保持开放；T-007 纳入连续布局、DMA 及

## 2026-10-06：A128 的局部 dense 重叠不等于完整阶段收益

- **研究者修正：**MFU 默认 extend 改为 A=128，history 仍为 64K；旧 A1024 报告
  不再代表当前默认。真实前三层普通追加与 C10 serving 替身继续分别验收。
- **新增证据：**当前四方法的正确性、独立计时、graph 节点与阶段覆盖已完成核验。
  第 1 层 extend 中，下一层完整历史 gather 的 52.51% 与当前层计算重叠；但 dense
  完整 extend 为 9.665 ms，高于 serial sparse 的 6.556 ms。ECHO 为 8.426 ms，
  仍未显示相对串行 sparse 的整体加速。局部重叠成立，全部等待已消除或方法获益的
  解释没有因此成立。
- **比较边界：**新旧 query、pool、驻留与计算图条件不同，不用旧两方法或 A1024
  数字宣称同配置加速。单次 profile 另有其他 GPU 活动，未量化其影响；正式 wall
  独立测量，不把两种测量的差值归为可移除 CPU 成本。
- **影响与任务：**更新 2.4、2.5、4.1–4.2。该次 MFU 更新时 C10 尚在补测；其后
  已发布 mapped-gather 版本，DMA 版本仍待完成，不由三层结果替代。
  T-007 的 NOSA indexer workspace 方案仍未实施。GR 场景、
  共同模型比较与质量结论的成熟度不变。依据见

## 2026-10-05：统一框架补测不等于方法收益或物理容量证明

- **原判断的更新：**最初入口整理只有 CPU 验证；统一框架重构后，各受影响路径
  已分别补独立数值、正式计时和 profile，最终覆盖范围见 S-031。旧数字仍属于其
  冻结来源，不将报告生成器或发布清理的后续修改写成此前捕获已执行的代码。
- **重构成本：**NOSA 三轮完整 trace 中位总耗时比 P0 增加 406.132 ms（0.19664%）；
  两模型的准入、清理及部分 candidate／复访阶段仍有残余开销。两模型各自全部
  128 个匹配请求的 cleanup 中位数增加，不因完整 trace 的较小变化而宣称没有代价。
- **适用范围：**A128 固定 serving 的 96 个适用内部样本全部未过双重 90% 门槛；
  A1024 冷并集单层回放的 9 个样本全部通过，最低 ratio 为 0.91081246。
  这支持局部设计的输入依赖，不能把单层收益改写为 serving 目标完成。
- **容量理解：**相同 P/NH 不等于相同物理分配。NOSA 随 session 分配 host backing，
  DeepSeek 使用全局 arena；逻辑 payload、cache 计费/预留与进程占用分开。
  本轮没有跑满 NH，没有新增真实 GR 代表性、质量或物理容量上限的证明。
- **任务边界：**T-007 的 indexer workspace 方案仍未实施，重构不代表完成这项
  优化。四个活动任务 T-006/T-003/T-007/T-002 保留，已完成的重构和报告工作移出
  待办；H64K-only、4K/16K 暂停、不跑满容量、固定 loop 及旧预算撤回等修正不变。
- **依据：**[S-031](sources.md#s-031统一框架补测与研究边界)绑定最终报告与独立复核。
  最终 API/profile 数值只取新验收来源；历史记录按原日期解释。

## 2026-10-05：按实验目的分类，区分数值验收与性能路径

- **研究者修正：**实验按四类定位：论文 motivation、baseline 实现性能合理性、
  服务后续设计的 sparse pattern、自有设计的性能 microbenchmark。当前最终关注
  性能，并提出将数值检查独立运行，避免每次实验重复携带完整验收。
- **判断更新：**不再仅以是否进入论文主线决定保留，也不先按现有目录机械合并。
  Baseline 检查要覆盖实际采用的实现、形状与路径，单独追求某个 MFU 数值不足以
  建立合理性；microbenchmark 与完整 motivation 分别解释局部和系统性能。
- **代码核对：**motivation 的 CPU 输出拷贝、完整数值比较和保存位于请求计时后，
  报告阶段还会重新比较。算子参考检查通常位于预热和计时前，部分模块比较与流量
  检查在样本间重复。这些增加总运行时间且可能扰动后续样本，没有独立占比测量。
  请求内 finite 归约/决策、allocator/事务校验及 FA3 repair 与上述参考测试分开。
- **建议与边界：**分离数值验收、正式性能、诊断 profile；同一实际执行实现及已覆盖
  配置可复用验收依据，数学、布局、调度或未覆盖路径变化时补相关检查。必要的计算、
  修复和同步不能随测试移除。现有报告的逐请求输出要求也须随拆分一并调整；本轮
  未修改测量代码、关闭运行时检查或生成新性能结论。
- **影响：**4.2–4.3；新增 T-008 梳理与拆分方案，现有 H64K 优化任务保持不变。

- **边界：**未改 cache 执行路径或新增测量；广泛 GR 策略暂不展开，现有 MFU 并行工作

## 2026-10-03：区分 prefill/extend 生命周期与 offload 策略

- **来自研究者：**猜测 ECHO prefill fetch 是给 chunked prefill 用的，询问仅有
  history prefill 与 candidate extend 的 GR 应如何 offload。
- **澄清：**chunked prefill 是典型用途；已有 offloaded prefix 的单次 extend
  同样适用。kernel 内 Q-block 流水线与 serving chunk 切分是两个层次。PD P 实例
  禁用 offload 不排除 GR 使用历史读回，论文 PD 主吞吐也不证明该路径的收益。
- **新增候选：**按冷构建、跨请求历史保留、candidate 工作集取数分别选择策略；比较
  预算内 resident build、冷热分级保留与 candidate 临时状态，并用整批唯一历史访问量
  比较整层提前预取、串行稀疏并集及重叠。以上是 agent 建议，尚未选择或实现。
- **保留边界：**当前仍为整用户 LRU；NOSA 无有限 page slots 或全局共享 staging，
  candidate 仍写入 host。ECHO/DeepSeek baseline 问题、场景代表性和容量压力均未因
  此次解释而解决。本轮仅论文/源码核对，没有新性能实验。
- **影响：**1.1、2.2–2.5、3.1–3.2、4.1–4.3；细化 T-003/T-007，保留 T-008。
  依据见 [S-015](sources.md) 和 [生命周期分析](gr_prefill_extend_offload.md)。

## 2026-10-02：研究者否定名义用户规模，要求有效的复访 miss
