# 四环节研究叙事草案

更新：2026-10-02。供讨论和组会使用，根据[当前状态](status.md)整理。
候选场景和动机仍待修正；这份草案保留已有设计先于场景确定的真实研究起点。

## 1. 任务、场景与研究问题

我们的研究从一个已有设计出发：让 sparse KV fetching 与 sparse attention 计算重叠执行。
目前正在考察 sparse attention GR serving 是否是合适的应用场景。希望理解，当多个用户或
请求的历史 KV 需要被保留时，怎样在 HBM 和 CPU DRAM 之间组织存储与执行，从而兼顾容量和服务效率。

一种候选方案是固定用户历史、每轮更新候选商品的 prefill 负载，利用复访时的历史 KV 复用。
项目已有对应请求生成工具，但场景还需要具体化：尚未确定推荐任务、模型、数据及服务负载
怎样对应，跨请求复用与服务评测也仍待建立。接下来需要比较可行的场景构造方案，并明确最终关注的服务目标。

## 2. SOTA baseline 与 Motivation

目前有一条需要逐项检验的候选论证。将 KV 全部存入 HBM 可以避免 offload 取数，但容量可能
限制可服务的用户或请求规模。将 KV 放入 CPU DRAM 可以扩大存储空间，却可能在执行中引入取数等待。
提前预取有机会隐藏等待，不过 dense prefetch 可能搬运最终不会使用的 KV；只取需要的 KV
能够减少这部分搬运，却又可能使取数与计算更难重叠。

这条论证的每一环都需要结合目标场景的分析和实验成立。ECHO 是重点比较对象：需要理解它
已经如何处理预取与稀疏选择，哪些问题仍然存在，以及当前设计能否在合理的共同条件下提供不同价值。
现有工程材料提供了探索基础，完整的 baseline 取舍和量化 motivation 尚未建立。

## 3. Challenge 与 Design

当前候选挑战是同时实现少搬运和有效重叠。需要进一步解释：当所需 KV 由稀疏选择决定时，
选集产生时机、数据依赖和可利用的计算窗口怎样限制提前取数，为什么简单的串行取数或预取
方案不足以解决目标场景中的问题。

已有设计联合组织 sparse KV fetching 与 sparse attention 计算，NOSA 路径已经提供局部实现
和性能支持。接下来需要从这些行为中提炼真正的技术困难，说明设计如何逐项应对，并与 ECHO
及其他相关方案比较。最终贡献的划分和名称仍有待形成。

## 4. Evaluation

已有固定输入的单层实验支持融合执行相对串行执行的局部收益。研究仍需要建立完整的服务
评测：容量是否影响服务规模，CPU DRAM offload 带来多少代价，当前设计能恢复多少服务效率，
以及与相关 baseline 相比有哪些优势和代价。

机制实验和消融应进一步解释减少搬运与重叠执行分别带来的影响，并考察不同容量、请求和
稀疏访问特点下的适用范围。模型与数据为何能代表目标场景，也需要在整体评测中交代清楚。
